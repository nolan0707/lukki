Claude Code 的权限管理机制是其“Harness（治理框架）”设计中最核心的安全屏障。它并非简单的“允许/禁止”开关，而是一套结合了静态规则、动态分类、模型自我审查及人工干预的多维度系统。
根据源码分析，其权限管理的实现可以从以下四个核心维度进行拆解：
1. 六种权限模式 (Permission Modes)
Claude Code 提供了六种不同的运行模式，以平衡开发效率与操作安全：
Default（默认模式）：交互式提示。对于敏感操作，系统会弹窗请求用户批准。
Auto（自动模式）：这是最先进的模式。系统利用 AI 分类器在不同思维层面检查操作的合法性。用户可以自定义识别危险权限的步骤。
Plan（规划模式）：在此模式下，任何执行操作前都必须经过显式的审批流程。
Bypass（绕过模式）：自动批准所有操作。此模式下几乎没有任何安全检查，属于极高风险模式。
DontAsk（自动拒绝）：虽然名字具有迷惑性，但在部分实现中被标记为“全盘拒绝（YOLO）”模式。
AcceptEdits（自动接受编辑）：专门用于文件编辑工具，允许 Agent 在不经询问的情况下直接修改代码。
2. 风险分级体系 (Risk Classification)
系统对每一个工具（Tool）的操作都进行了风险定义，将其标记为不同的等级，从而决定触发哪种审批逻辑：
LOW（低风险）：通常指只读操作（如 FileReadTool），系统可能默认放行。
MEDIUM / HIGH（中高风险）：涉及系统状态变更的操作（如 BashTool 执行 Shell 命令、修改敏感配置文件）。这类操作必须触发权限检查器。
3. 多层拦截与校验流程 (Decision Flow)
每当 LLM 尝试发起一个工具调用（Tool-call）时，QueryEngine 会截获 canUseTool() 调用，并引导其进入以下校验管道：
输入校验 (validateInput)：使用 Zod 模式验证进行“预检”。如果模型生成的参数格式不正确或试图访问越权路径（如通过 URL 编码绕过目录限制），操作将被立即拦截。
权限评估 (checkPermissions)：
静态规则检查：检查 .claude.json 或设置中的黑白名单。例如，.gitconfig、.bashrc 等敏感文件被严格保护，禁止自动编辑。
ML 分类器决策：在自动模式下，系统会调用一个快速的 ML 模型（YOLO 分类器）来判断当前上下文下的操作是否安全。
用户解释器：如果需要人工介入，系统会调用另一个专门的 LLM 实例来分析工具风险，并用人类可理解的语言向用户解释“为什么要执行这个操作”。
4. 针对特定工具的硬核防御 (Hardened Defense)
针对风险最高的 BashTool（Shell 执行），Harness 实现了 AST 级别的深度治理：
AST 审计：系统内置了 Shell AST（抽象语法树）解析器。在执行前解析命令结构，精准识别混淆后的危险行为，如 rm -rf /、sudo 提权、Fork 炸弹或 TTY 注入。
时间预算拦截：为了防止模型通过长阻塞指令耗尽系统资源，沙箱甚至拦截了所有 sleep 时间超过 2 秒的指令。
提示词注入防御：利用 partiallySanitizeUnicode() 函数对输入进行净化，剔除隐藏的 Unicode 字符，防止攻击者通过“Unicode 走私”绕过权限检查。
5. 协作模式下的“信箱审批” (Mailbox Pattern)
在多代理协作（Coordinator-Worker）架构中，权限管理呈现出层级化特征：
信箱模式：执行具体任务的 Worker Agent 没有任何独立审批权。当它需要执行高风险操作时，必须将请求发送到主代理（Coordinator）的信箱中。
原子申领 (Atomic Claim)：确保在并行执行时，两个代理不会同时处理同一个审批请求，保证了复杂任务流中的权限确定性。
总结建议：Claude Code 的权限管理实现证明了其 “怀疑论（Skeptical）”设计哲学：即绝对不信任模型的道德自觉，而是通过 2.9 万行代码构建的 Tool.ts 基类 强制执行一套严密的、基于 AST 和模式验证的物理约束。
