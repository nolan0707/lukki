以下是 QueryEngine 实现机制的详细说明：
1. 核心交互：异步生成器驱动的流式循环
QueryEngine 的底层是一个异步生成器（Async Generator）。这种设计允许系统在接收到 Anthropic API 的响应时，能够将令牌（Tokens）实时“产出”并推送到 UI 层进行流式渲染，从而实现极佳的终端交互体验。
2. 代理行为：工具调用循环（Tool-call Loops）
QueryEngine 实现了典型的“思考-行动-观察”循环，其自主性体现在对工具调用的调度上：
循环迭代：当 LLM 发出工具调用请求（如读取文件或执行 Bash 命令）时，QueryEngine 会暂停流式传输，转而执行相应的工具。
状态闭环：工具执行的结果（tool_result）会被重新注入到对话历史中，QueryEngine 随后再次发起 API 请求，直到模型不再请求工具并返回最终文本响应为止。
3. 智能推理：思考模式（Thinking Mode）管理
QueryEngine 负责管理 Claude 的深度推理能力：
思考块处理：它能够识别并处理响应中特殊的 <thinking> 块，支持扩展推理逻辑。
自适应思考：在最新的实现中，它配合 API 参数（如 effort）来平衡推理深度与响应速度。
4. 资源治理：Token 计数与“自愈”查询循环
QueryEngine 承担了精细的上下文窗口管理职责，以应对长会话带来的挑战：
实时 Token 监控：它持续跟踪输入、输出及缓存的 Token 消耗。
自愈式压缩（Self-healing Loop）：这是其架构中的精妙之处。当上下文接近限额时，引擎不会崩溃，而是会自动触发上下文压缩（Compaction）。
缓冲管理：它会在触达天花板前预留约 13,000 个 Token 的安全缓冲带，专门用于生成结构化摘要，确保压缩操作本身有足够的 Token 空间完成。
5. 可靠性与安全性：权限包装与重试逻辑
QueryEngine 充当了 LLM 与本地系统之间的“安全检查站”：
权限包装（Permission Wrapping）：它拦截每一次 canUseTool() 调用。在工具真正执行前，必须通过 QueryEngine 触发权限评估策略（如自动模式、手动审批等）。
鲁棒性设计：为了应对工业级环境的复杂性，它内置了完善的重试逻辑，能够处理频率限制（Rate Limits）、瞬时网络故障及流式传输错误。
6. 设计哲学：集中化治理
将如此庞大的逻辑集中在 QueryEngine.ts 中是一个深思熟虑的工程决策。这种做法确保了无论是重试策略、预算控制还是错误处理，在处理不同任务时都能保持高度的一致性。这体现了 Claude Code 的核心哲学：模型是易碎且不可预测的，因此必须由一个极其强健、确定性的 Harness（马具/治理框架） 来进行约束和驱动。
