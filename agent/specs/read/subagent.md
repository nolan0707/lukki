在 Claude Code 的架构设计中，SubAgent（子代理） 的实现机制是其能够处理复杂工程任务的核心。它并非一个独立的、与主程序并行的复杂系统，而是通过 “Harness（治理框架）” 将代理能力原子化，实现了一种高度可扩展的协作模式。
以下是 SubAgent 实现机制的详细拆解：
1. 核心触发机制：AgentTool 与“平坦架构”
Claude Code 最具创新性的设计之一是将子代理的派生视为一种普通的工具调用。
工具化派生：系统内置了一个名为 AgentTool 的工具。当主代理（Coordinator）判断任务需要并行处理或需要隔离执行时，它会像调用“读取文件”工具一样调用 AgentTool。
平坦架构设计：这种设计使得系统无需复杂的协调层。子代理是工具注册表中的“一等公民”，这种扁平化设计让架构变得简单且可预测。
2. 编排模式：协调者与工作者（Coordinator-Worker）
当启动 “协调者模式”（Coordinator Mode） 时，Claude Code 的运行逻辑会发生根本性转变：
任务拆解：主代理充当协调者，将大任务拆解为子任务，并分配给多个并行的 Worker Agents（工作者代理）。
标准协作流程：典型的协作周期包括：调研（Research）（并行调研代码库）→ 综合（Synthesis）（由协调者汇总并制定方案）→ 执行（Implementation）（子代理执行变更）→ 验证（Verification）（子代理运行测试）。
并行计算：源码明确强调“并行是超级力量”，鼓励工作者异步执行任务，避免串行工作浪费资源。
3. 通信与隔离机制
为了确保多个代理在同一个代码库中协作而不产生冲突，系统设计了严密的隔离与通信协议：
XML 消息通信：代理之间通过特定的 XML 格式消息（如 <task-notification>）交换任务状态、摘要和 Token 消耗等信息。
上下文隔离与共享：每个子代理拥有独立的上下文（Context），利用 AsyncLocalStorage 或不同的进程（如 tmux/iTerm2 面板）实现隔离。
共享暂存区 (tengu_scratch)：系统为代理间提供了一个专门的暂存目录，用于存储和共享持久化的中间知识，而不直接污染主记忆。
4. 成本优化：Prompt 缓存共享
在多代理架构中，最昂贵的是 Token 消耗。Claude Code 通过以下方式优化：
缓存重用：多个代理共享同一个 Prompt 缓存（Prompt Cache）。这意味着它们在处理同一个项目时，不需要重复支付加载项目背景（如 CLAUDE.md 或文件结构）的 Token 成本。
5. 安全治理：信箱审批模式（Mailbox Pattern）
为了防止子代理在自动执行时失控，系统引入了**“信箱模式”**：
风险隔离：执行具体任务的 Worker 无权独立批准高风险操作（如删除文件或执行 Bash 脚本）。
异步审批：Worker 必须将高风险请求发送至协调者的“信箱”。协调者对请求进行评估，批准后再由 Worker 执行。
原子申领（Atomic Claim）：这一机制确保在并行环境下，同一审批任务不会被多个 Worker 重复处理，保证了状态的确定性。
6. 自主性约束
系统在 Prompt 中明确规定了子代理的行为边界，以防止出现**“懒惰代理”**或死循环：
禁止二次委派：禁止子代理简单地说“基于你的发现”，而是要求其阅读实际调研结果并给出明确指令。
禁止特定工具：子代理通常被禁止使用 AskUserQuestion（询问用户）或 ExitPlanMode（退出计划模式）等关键工具，以防干扰主进程的逻辑流。
综上所述，Claude Code 的 SubAgent 机制是通过 AgentTool 原子化调用、并行 Worker 异步执行以及信箱审批模式安全管控三者结合实现的工业级 Agent 协作方案。
